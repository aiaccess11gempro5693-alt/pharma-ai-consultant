# Решения по концепции

Статусы: **принято** — согласовано внутри команды; **предложено** — ждёт подтверждения.

## Блок А. Концепция — принято (30.09.2026)

1. **Основа — атомы.** Это перенос практики отделов медицинской информации (заранее согласованные стандартные ответы), понятной юристам и медотделу. Условия: точный классификатор, память контекста диалога, атомы — законченные предложения.
2. **База знаний — только согласованные атомы**, в любом режиме. RAG по сырым документам не используем: даже официальные описания содержат лечебные утверждения (у Статинориса — «противоопухолевые свойства», «предотвращает инфаркт»). Вопрос «RAG или атомы» сводится к двум выборам: откуда знания (всегда атомы) и кто пишет текст («Контроль» — скрипт, «Живой диалог» — модель с проверкой).
3. **Маршрутизация по теме, а не по названию продукта.** Всё про здоровье, самочувствие, симптомы, анализы, дозы, состав, приём → атомный режим. При сомнении — атомный режим. Режим «липкий»: остаёмся в нём, пока тема явно не сменилась. Фильтр жалоб на самочувствие стоит до любой маршрутизации.
4. **Свободный слой не утверждает фактов.** Факты и «идеология» бренда — атомы уровня «бренд». Свободному слою остаются приветствие, уточнение, навигация, вежливый отказ, реакция на провокации — библиотека служебных фраз. Итог: «два слоя» = атомы + вежливая обвязка. Нужно проговорить с Олегом (см. open-questions.md).
5. **В схему добавляем:** фильтр жалоб первым шагом с адресатом у клиента; состояние диалога (продукт, аудитория, предыдущие намерения); проверку статуса врача/медпреда; служебный ответ на присланные анализы и цифры; очередь вопросов без ответа → кандидаты в атомы; передачу живому человеку (горячая линия); вопрос ответственности за неверный атом — в договор.

## Блок Б. Атомы и формулировки — принято (30.09.2026)

1. **Планка — до ~1000 атомов на продукт** (ориентир для всей фармы, включая лекарства; сложные препараты по хендоверу до 1000–1500). Для БАД ожидаем меньше, реальную цифру по Статинорису покажут прогоны.
2. **Один факт — один атом.** Варианты по аудиториям заводим только там, где формулировка действительно должна отличаться (например, состав для покупателя и для врача).
3. **Переиспользование между продуктами не обещаем, а измеряем.** Первая пара: Статинорис → Статинорис Форте (ожидаем высокое, ~70%). Между разными категориями переходят в основном атомы бренда и служебные фразы.
4. **Текст атома не меняется, склонений нет.** Гибкость — в связках: вводная связка перед атомом, атом всегда заканчивается точкой, атомы не склеиваем в одно предложение. Нужна другая грамматическая форма → отдельный согласованный атом-вариант.
5. **Цвет = уровень риска, а не только источник:**
   - зелёный — дословно из этикетки, инструкции или СГР, без утверждений об эффекте;
   - жёлтый — сокращение или перефраз официального текста без изменения смысла и цифр;
   - оранжевый — сайт и маркетинг, а также сторонние справочники (РЛС, Видаль) до сверки с упаковкой;
   - красный — утверждения об эффекте на здоровье, взаимодействия с лекарствами, наши формулировки, всё из стоп-листа, даже если оно есть в официальном документе.
   Пока у нас нет документов клиента, всё собранное по Статинорису — максимум оранжевое.
6. **Юристы видят все атомы.** Таблица отсортирована по цвету: зелёные подтверждают списком, основное время — на жёлтые, оранжевые, красные.

## Блок В. Модель — принято (30.09.2026)

1. **Классификатор двухшаговый.** При сотнях намерений лёгкая модель путается в длинном списке. Поэтому: поиск по эмбеддингам отбирает 10–20 похожих намерений → лёгкая модель выбирает одно и возвращает JSON. Стоимость и точность не зависят от размера базы.
2. **Уверенность — по косвенным признакам**, а не по самооценке модели (она почти всегда пишет «0,95»): близость вопроса к намерениям по эмбеддингам и совпадение ответов при 2–3 прогонах. Порог настраиваем на тестовом наборе с ловушками.
3. **Фильтр жалоб — отдельная простая проверка**, настроенная ловить с запасом: лишняя передача в отдел качества лучше пропущенной жалобы.
4. **Код не привязан к модели.** Модель подключается через одну прослойку и меняется настройкой. Варианты: GigaChat / YandexGPT; открытая модель (например, Qwen) в российском облаке; зарубежная модель — только для тестов на синтетике. Вопрос 152-ФЗ решают юристы клиента, но он не блокирует разработку.
5. **Прогоны разделяем.** Генерация вопросов и черновиков атомов — на любой модели (токены Олега). Настройка классификатора и порога — на модели-кандидате для прода: пороги с одной модели на другую не переносятся.

## Блок Г. Конвейер — принято (30.09.2026)

1. **Вопросы генерируем по смыслу, по ролям и каналам.** Ориентир — около 1000 разных смыслов (намерений); для одного БАД их может оказаться меньше, реальную цифру покажут прогоны. На каждый смысл — 3–5 формулировок (коротко, разговорно, с опечаткой, в составном вопросе): они нужны не для атомов, а для проверки, что бот узнаёт смысл в любой форме. (принято, 30.09.2026)
3. **Покрытие проверяем через разметку.** У каждого вопроса — ожидаемые намерения и ожидаемый ответ (атомы или служебная фраза). Черновик разметки делает модель, человек проверяет выборку. Отчёт о покрытии: вопросы без намерения, намерения без атомов, атомы, не нужные ни одному намерению. Вопросы делим на три набора: для настройки, отложенный для финальной проверки, ловушки. (принято, 30.09.2026)
2. **Реальные вопросы (маркетплейсы, отзывы, горячая линия) пока не берём.** Решаем на этапе реализации. (принято, 30.09.2026)
5. **Всё храним в репозитории.** Нужна ли юристам таблица — решим позже. (принято, 30.09.2026)

Источники до материалов клиента (Г4) — в open-questions.md.
